# Spec for Motor Controller Custom Firmware

Currently, this site interfaces with a USB debugging module to change the firmware on the ebike's display module. A new, better method has been developed to modify the firmware on the bike's motor controller that works over BLE (through the display module.)

The display firmware is now obsolete, but should be available. The new firmware, however, should be the recommended path. This spec is for converting the research code in scratch/flash-poc to a production quality flash utility that works as a CLI and on the web via the web bluetooth api (Chrome exclusive currently, similar to web USB).

At a high level, we'll need to integrate the poc into this codebase. We'll first want to create a package in /packages to support shared BLE utilities for use in both the cli and web interfaces (ble-utils). This package will contain the details on how to interact with the BLE protocols used to read version info and to execute the DFU process. This includes BLE service/GATT information, how to convert data, and any other platform agnostic processes. Tests should be added/copied when possible. Look at the current 'core' package as a reference.

The current 'core' package should be split out into 'core' and a usb-utils package. 'core' will contain any common utilities between the two delivery methods. However, it's possible there will be no common code, in which case just rename core to usb-utils.

Next, the firmware patching script (scratch/flash-poc/scripts/patch_controller.ts) for the motor controller will need to be integrated into the apps/kitchen package. The patching process for the display and controller will largely be the same, but the core of the current controller patching script will need to be extracted and utilize the helper utilities in kitchen. Note that unlike the nrf firmware, the controller firmware does not need any 'cleaning'. Currently, only the 'firmware/mc/230-BLUETOOTH-EXT1-310' firmware is supported. Validate by running the poc patch script on firmware/mc/230-BLUETOOTH-EXT1-310/GD_S73Rx_H104_S310US_20221020.bin and ensure the migrated code produces a byte exact output. Kitchen could also use a README.md.

Next the poc cli will need to be refactored and production-ized, then ported to a new app, 'mc-farm'. The current 'farm' app should be renamed to 'nrf-farm'. It's unlikely these two apps will share much except by what's already in the 'core' package, but if there are any sharing opportunities, share that code by moving it into the appropriate /package folder.

The 'mc-farm' cli will have 2 core functions; read version info and flash firmware. There's currently no way to read firmware off the motor controller. This cli should take a subcommand and an advertised BLE name, plus any arguments required for that specific sub command. Not all arguments in the poc code are needed, but for flashing, a dry run should be the default. The mc-farm will also need a readme.

Finally, the 'web' app will need to be updated to run the read info and dfu process. We'll refactor the web app to 'demote' the current USB method in favor of the BLE method. The BLE method is much simpler, but we'll follow a similar UX as the USB method; a user friendly step-by-step version, and an advanced page with tools for advanced users. This part is more involved and still needs conceptual development. It's included in this spec for completeness, but it not ready to implement yet.
